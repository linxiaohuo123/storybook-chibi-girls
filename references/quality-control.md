# 自检、客户验收与定向修复

## 看实际图，不看指令是否写全

以本单适用要求检查实际输出。没有图片、看不清或只拿到提示词时写 `not_reviewed`；不能把“未发现问题”扩张为自动证明不存在。仅改配色且保留竖幅原图时，不用默认方图规则误判编辑失败；保留的范围外问题如实记录。

先按预期观看尺寸看整体；尺寸未知时可参考约 256 px 的缩略显示检查可读性，再看原始分辨率局部。这是检查方法，不是合格像素规格。不得用生成式放大改变检查证据。

## 第一层：硬约束

| 项目 | 观察内容 | 失败时处理 |
| --- | --- | --- |
| 主体与画幅 | 独立全身少女、约定比例与方图、帽饰道具鞋完整 | 调整构图，不拉伸、硬裁或改变身份 |
| 背景 | 纯白不透明，无文字、编号、场景、边框 | 只修背景干扰，保留浅色衣物与空隙 |
| 头发 | 均匀平涂，无亮带、渐变、暗面、反光、颗粒 | 用原基底色去光影，保留发束轮廓 |
| 无白边无影子 | 无贴纸光圈、灰椭圆、投影、环境遮蔽 | 定向去除，不削鞋底、不抹白色蕾丝 |
| 线条 | 无悬空线、双描边、穿透线、来源不明的饰带 | 指定具体部位清理，保留有意义细节 |
| 结构与穿搭 | 领袖连续、衣层扣合成立、带子有端点、手与道具接触合理 | 只修问题连接及相邻结构 |
| 情绪 | 正向自然，惊喜不恐惧、害羞不委屈 | 调整眼眉嘴，保持人物身份 |

硬条件明显失败时整图不能标记通过，没有用总体高分抵消高光或裁脚的规则。头发内部轻微明暗仍需按本单严格程度检查，不因“看起来不错”自行放宽用户的纯平涂要求。

## 第二层：订单设计适配

| 项目 | 可观察的检查 | 不足时如何改 |
| --- | --- | --- |
| 幻想可见 | 去掉角色名，主道具或服装仍体现超出日常换装的设定 | 改可见机制和主形，不用背景、光效补故事 |
| 穿搭完整 | 内搭、主衣、外层、鞋袜属于一套能穿的衣服，手够得到道具 | 改剪裁、固定点或持物位置 |
| 细节层级 | 缩略图看清脸、轮廓和动作；放大能解释花边与扣件 | 集中焦点、保留安静布面，不全图加饰品 |
| 配色 | 主辅明确，接触边界可辨，无深色聚团、发灰或处处抢眼 | 按部位调整色相、明度与面积，不全图套滤镜 |
| 单组一致 | 比例、五官语言、线条和平涂一致 | 修风格漂移，不把角色全部改成同一张脸和姿态 |
| 跨角色差异 | 发型外形、服装主形、手臂位置、表情、主道具实际不同 | 改可见结构，不靠同义词／新名字通过 |
| 跨组差异 | 世界规则、服装语言、色彩关系有区别 | 重排分组，不继续复制同款裙装 |

记录具体可见现象与修改动作，不给未经校准的“审美 95 分”。风格、配色是否最终满足客户需客户反馈，不能由脚本或助手替客户确认。

## 只读文件检查

实际本地输出已可访问时运行：

```bash
python3 scripts/check_image.py /absolute/path/image.png --require-exact-white-border
```

依赖 Pillow。脚本只读尺寸、帧数、透明度、近白／精确白边带比例与非白包围盒，不修改像素。

- 默认近白检查允许容差；`--require-exact-white-border` 要求全部被采样边带像素 RGB 恰为 255。
- 精确白边带仍不证明整个背景纯白；角色附近、裙摆空隙、头发空隙须另外检查。也不证明没有阴影或白边。
- 正方形只证明宽高相同；包围盒无法区分主体、页码和阴影。浅色衣物与细线会影响启发式判断。
- 脚本不识别性别、服装合理性、幻想、表情、杂线或审美。成功状态始终需要视觉检查。
- 仅改色且明确保留非方形原图时，脚本报告的非方形是事实，不代表本次任务失败。
- 无可访问文件或依赖不可用时标记像素检查不可用，不绕过生成工具的展示保存规则，不捏造输出。

`scripts/check_diversity.py` 比较规范化字段，不看图；它的覆盖和历史质量过滤不等于成图差异或客户验收。见 [character-design.md](character-design.md)。

## 修复预算与复检

首次生成后每张默认最多 2 次定向修复。先定位问题，写出保持项，只改所需区域；每次看修改区、相邻结构以及范围外是否漂移。图像工具不能保证逐像素不变，发现身份或结构漂移要如实记录。

同类失败重复出现时，先检查参考图是否携带渐变、阴影或复杂杂线，提示词是否塞入过多冲突要求。去高光时优先仅以当前成图为编辑目标，不再加入带高光的原始参考。首批持续硬失败时停止扩量并说明已完成、待处理和具体原因，不无限重抽。

## 状态与反馈

`generation_status` 记录计划／已生成／阻塞；`quality_status` 记录自检；`client_status` 记录真实客户反馈。样例和保存方式见 [production-workflow.md](production-workflow.md)。

全部适用项目经实际看图通过后才写 `quality_status: passed`。客户接受必须有明确反馈；缺失为 pending 或历史 unknown。`known_issues: []` 在未检查时只代表未记录，不表示没有问题。
