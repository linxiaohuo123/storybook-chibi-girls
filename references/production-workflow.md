# 多组制作与接单流程

将此流程作为可调整的生产默认，不冒充客户原始要求。小单只保留必要字段；大单按项目持续记录，避免每轮重新解释。

## 1. 固定本单简报

整理已有信息，能从上下文确定的直接填写。只询问会实质影响交付且无法合理决定的问题，不把简报变成强制问卷。

| 字段 | 内容与证据 |
| --- | --- |
| 项目、数量、分组 | 稳定 `project_id`、总张数、每组张数；未指定数量不自行承诺大批量 |
| 硬要求 | 主体、画幅、背景、头发、禁用内容；标明用户明示或沿用默认 |
| 画风锚点 | 1～2 个实际可访问参考；分别标注用途、明确认可的部分和不继承部分 |
| 设计方向 | 幻想程度、服装方向、细节密度、色彩偏好；推断标为建议 |
| 变化范围 | 允许变化的发型、配色、服装、动作；需固定的脸部语言、线条等 |
| 交付规格 | 实际要求的像素、文件类型、命名；1:1 不自动意味着某个像素值 |
| 验收方式 | 自检完成或需要客户逐组确认；没有回复就是 `pending` |

聊天截图看不清的句子记为待确认，不逐字编造。整张样图获一句“可以”也不能推出每个像素均符合本单规范；按反馈上下文记录认可范围。

## 2. 分组与出样

先为所有组分配主题世界、服装语言、轮廓、主辅色关系与细节重点，再写角色。组内共享画风和一个主题规则；每个成员的子身份、道具功能、发型、动作不同。组间至少在主题机制、服装轮廓语言、色彩关系中有实质区别，不能只换组名。

- 例：30 张、5 组，每组 6 人。先列 30 行简短设计表，每组挑 1 个能代表该组主要风险的角色出样；每个样张算入总数，不额外重复生成同一角色。
- 已有稳定锚点且同组续做时，不必重新出完整试样组。缺少新组画风参照时，用既有画风搭配新服装方向，不让风格漂移。
- 样张自检通过后按 3～6 张小批推进；这只是便于复查的默认，不是平台并发参数或强制审批门槛。实际调用遵守工具能力。
- 用户要求先交方案就停在方案；要求完整批量则继续完成，除非硬失败持续出现、工具阻塞或用户要求等客户确认。
- 对客户尚未确认的方向注明状态。不能把“继续出图”写成“客户已经接受”。

## 3. 保存可续做记录

默认将私有项目资料放在当前环境支持的持久项目位置；已有外部项目目录就沿用。个人技能只保存通用方法与模板。客户聊天、PDF、原始订单、失败样张和历史不要发布到技能的公共仓库。

可用三个逻辑文件（不要求机械创建空文件）：

- `brief.json`：本单要求、版本和证据位置。
- `plan.json`：`mode`、项目/系列信息、全部角色卡，角色字段见 [character-design.md](character-design.md)。
- `history.jsonl`：实际生成或收到反馈的版本，一行一版；写入前核对既有记录，不覆盖旧版本。

每个角色版本使用稳定 `id`、独立 `revision_id` 与可选 `parent_revision_id`。例如角色 `g02-c04` 的改色版为 `g02-c04-r02`；改色不算另一个新角色。建议文件名 `g02-c04-r02.png`，不得谎称尚不存在的文件已保存。

```json
{
  "project_id": "fantasy-series",
  "series_id": "g02",
  "id": "g02-c04",
  "revision_id": "g02-c04-r01",
  "generation_status": "planned",
  "quality_status": "not_reviewed",
  "pixel_check": "unavailable",
  "visual_review": {"status": "not_reviewed", "issues": []},
  "client_status": "pending",
  "image_ref": null,
  "prompt": null,
  "feedback": []
}
```

这是状态片段，合并到完整角色卡使用；不能把它直接当作新角色去重计划。`image_ref` 只写实际可访问的标识；未产出时保持 `null`。`prompt` 记录实际提交内容，模型/seed 只在工具实际返回且必要时保存。

## 4. 区分三种状态

| 状态 | 取值 | 何时能更新 |
| --- | --- | --- |
| `generation_status` | `planned / generated / blocked` | 只有实际图像返回才是 generated |
| `quality_status` | `not_reviewed / passed / failed` | 对实际图片完成全部适用自检后；不能用提示词或脚本出口码代替 |
| `client_status` | `pending / accepted / revision_requested / rejected` | 只有实际用户或客户明确反馈支持时；自检不能自动设置 accepted |

既有历史没有客户状态就视为未知，不补写 accepted。未检查、失败稿可以记录，不能混进合格样张池；已自检但未获客户接受的图不能冒充客户锚点。去重脚本使用的视觉历史与客户验收池是不同用途。

## 5. 把反馈变成明确修订

每条反馈记录：来源、对应图片版本、原意、作用范围、修改部位、必须保持项、处理结果。范围默认限于明确提到的角色或组；跨项目长期规则须有明确支持。

| 反馈 | 先诊断 | 定向动作 |
| --- | --- | --- |
| 太日常 | 幻想是否只在名字里；去掉文字还能看出吗 | 改道具功能与服装结构；不要只加星星或换职业名 |
| 不够精致 | 缺少轮廓层次，还是局部过空 | 增加一个有用途的主装饰及少量呼应，不全图加线 |
| 穿搭怪 | 层次、固定点、材质或活动是否矛盾 | 调整问题层或扣合，保留其他设计 |
| 配色不好 | 深色聚集、色相争夺、发灰或过淡 | 修改对应部位的色彩关系，不默认全图降饱和 |
| 线条奇怪 | 指出图上具体位置 | 修悬空线、穿透线、重描和失去结构的褶皱 |
| 太像前一张 | 比较可见轮廓、道具功能和动作 | 修改新角色的结构差异，不靠重命名 |

修订后再次检查修改区及相邻结构，并对照修改前确认范围外未明显漂移。保留旧版，不把待验收新版覆盖成唯一可追溯版本。
